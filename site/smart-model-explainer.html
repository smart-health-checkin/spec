Model explainer

The check-in request and response

A clinic app sends a list of items it would like. The patient's health app shows the list, the patient decides what to share, and the health app answers with records and one outcome per item. This page walks through that JSON with one running example. Every example on it is checked against the client library's validators when the site is built.

At a glance

A clinic asks for five items. The patient shares four of them and declines insurance. Every item id appears once in the outcomes. Records name the items they answer. Point at an id to follow it across.

Request items[]

  • Patient demographicspatient
  • Insurance cardinsurance
  • Medicationsmedications
  • Immunizationsimmunizations
  • Depression screening formintake

Response artifacts[]

  • FHIR BundlePatient and two MedicationRequestspatientmedications
  • SMART Health CardSigned immunization recordimmunizations
  • FHIR BundleOne Immunization not on the cardimmunizations
  • QuestionnaireResponseThe patient's answersintake

Response requestStatus[]

  • patient fulfilled
  • insurance declinedNo record is returned for it.
  • medications partialOne medication was kept private.
  • immunizations fulfilled
  • intake fulfilled

Two rules hold the model together. Every item gets exactly one row in requestStatus[]. Every record lists the item ids it answers in fulfills[]. One record can answer several items, and one item can be answered by several records.

The request

The app builds this object and hands it to the health app.

{
  "type": "smart-health-checkin-request",
  "version": "1",
  "id": "checkin-7f3a",
  "purpose": "Clinic check-in",
  "fhirVersions": ["4.0.1"],
  "items": [ … ]
}
type
Always smart-health-checkin-request.
version
Always "1".
id
Chosen by the app. The response echoes it back as requestId.
purpose
Why the app is asking, shown to the patient.
fhirVersions
The FHIR releases the app can read.
items
What the app would like, one entry per thing the patient reviews.

An item

Each item is one thing the patient reviews and one row in the outcomes.

{
  "id": "insurance",
  "title": "Insurance card",
  "summary": "Used for billing today's visit",
  "required": true,
  "content": {
    "kind": "selection.fhir",
    "profiles": ["http://hl7.org/fhir/us/insurance-card/StructureDefinition/C4DIC-Coverage"]
  },
  "accept": ["application/fhir+json"]
}
id
Short and unique within the request. The response refers to the item by this id.
title
What the patient sees.
summary
Optional. One more line for the patient.
required
Optional. Tells the patient the clinic needs this item.It is advice only. The patient can still decline, and the health app can still answer unavailable.
content
What is being asked for. See the next section.
accept
Media types the app can read for this item, most preferred first.

What an item can ask for

content.kind is either selection.fhir (share records the patient already has) or form.fhir (fill in a form). A health app that sees a kind it doesn't know answers unsupported for that item and handles the rest of the request as usual.

An exact profile

Records that claim this StructureDefinition in meta.profile. List several to accept any of them.

{
  "id": "patient",
  "title": "Patient demographics",
  "content": {
    "kind": "selection.fhir",
    "profiles": ["http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient"]
  },
  "accept": ["application/fhir+json"]
}

Keep canonical strings exactly as written, including any |version. A health app must not strip the version to look the profile up, and must only report fulfilled for a versioned profile when the records claim that same version. Spec §5.5

A profile family

Any profile from an implementation guide, such as all of US Core. Add resourceTypes to narrow it. If profiles is also present, it widens the match rather than narrowing it. 

{
  "id": "medications",
  "title": "Medications",
  "content": {
    "kind": "selection.fhir",
    "profilesFrom": ["http://hl7.org/fhir/us/core"],
    "resourceTypes": ["MedicationRequest"]
  },
  "accept": ["application/fhir+json"]
}

No filter

Leave out all three filters to let the patient and their health app decide what's relevant for the visit. Partial answers are expected. 

{
  "id": "anything-helpful",
  "title": "Anything else that would help your visit",
  "content": { "kind": "selection.fhir" },
  "accept": ["application/fhir+json", "application/smart-health-card"]
}

A form by URL

The health app finds the Questionnaire from its canonical URL, shows it, and returns a QuestionnaireResponse whose questionnaire is the same string. If it can't load the form, it answers unsupported or error rather than guessing. 

{
  "id": "intake",
  "title": "Depression screening (PHQ-2)",
  "content": {
    "kind": "form.fhir",
    "questionnaireCanonical": "https://smart-health-checkin.org/connectathon/Questionnaire/phq-2.json"
  },
  "accept": ["application/fhir+json"]
}

A form, inline

Send the whole Questionnaire when it isn't published anywhere. You can send both: the canonical names the form and the inline copy is what gets shown. 

{
  "id": "visit-reason",
  "title": "Reason for today's visit",
  "content": {
    "kind": "form.fhir",
    "questionnaire": {
      "resourceType": "Questionnaire",
      "status": "active",
      "item": [
        { "linkId": "reason", "text": "What brings you in today?", "type": "string" }
      ]
    }
  },
  "accept": ["application/fhir+json"]
}

What the patient sees

  1. The health app shows the purpose and each item's title and summary.
  2. For each item it finds matching records, or shows the form.
  3. The patient shares, leaves out, or fills in each item. They can share less than was asked for, and the health app can offer other records that would help.
  4. The health app sends back the records and one outcome per item.

Text in the request is not proof of who is asking. The browser and the wallet's trust decisions establish that, outside the JSON, so the request must not carry names, logos, or URLs claiming to identify the clinic. Spec §5.7

The response

{
  "type": "smart-health-checkin-response",
  "version": "1",
  "requestId": "checkin-7f3a",
  "artifacts": [ … ],
  "requestStatus": [ … ]
}
requestId
The request's id, exactly.
artifacts
The records the patient shared. Can be empty.
requestStatus
One outcome for every item in the request.

A record

The JSON calls each shared record an artifact. Two formats are defined.

FHIR JSON 
{
  "id": "a1",
  "mediaType": "application/fhir+json",
  "fhirVersion": "4.0.1",
  "fulfills": ["patient", "medications"],
  "value": {
    "resourceType": "Bundle",
    "type": "collection",
    "entry": [ … ]
  }
}
SMART Health Card 
{
  "id": "a2",
  "mediaType": "application/smart-health-card",
  "fulfills": ["immunizations"],
  "value": {
    "verifiableCredential": ["eyJ6aXAiOiJ…"]
  }
}
id
Unique within the response.
mediaType
application/fhir+json or application/smart-health-card.It must be in the accept list of every item the record fulfills.
fulfills
The item ids this record answers. At least one.
fhirVersion
FHIR JSON only. A health card carries its FHIR version inside the signed card.
value
For FHIR JSON, a resource or a Bundle. For a health card, the card file's JSON.

Outcomes

Each item gets one row, whether or not any record came back for it.

{ "item": "medications", "status": "partial", "message": "One medication was kept private" }
StatusMeaningFor example
fulfilledShared what was asked for.The insurance card was shared.
partialShared some of it.Two of three medications were shared.
declinedThe patient chose not to share.The patient turned off the insurance card.
unavailableThe health app has nothing that matches.No immunizations are on file.
unsupportedThe health app can't handle this kind of item.An unknown content.kind, or a form it can't load.
errorIt tried and failed.The patient portal behind it timed out.

fulfilled and partial should come with at least one record that lists the item. The others usually come with none.

What the app checks

Before using a response, the app checks it against the request it sent. The client library does this for you. The Testing EHR runs the same checks against your health app.

  • requestId equals the request's id. §6.4
  • Every item has exactly one outcome, with no unknown or repeated ids. §6.4
  • Every id in fulfills[] is an item in the request. §6.4
  • Every record's mediaType is accepted by each item it fulfills. §5.6
  • FHIR JSON has a fhirVersion, and a Bundle doesn't mix releases. A health card has no outer fhirVersion. §6.4
  • Returned meta.profile strings and QuestionnaireResponse.questionnaire are kept exactly as written, and a record only counts toward a versioned profile (…|1.2) if it claims that exact version. §5.5
  • Several records for one item are allowed, and the app looks at all of them. §6.3

Passing these checks means the response is well formed. Whether to trust a health card's issuer or to file a record into the chart is up to the clinic.
